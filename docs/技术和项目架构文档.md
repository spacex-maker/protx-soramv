# AI2OBJ 技术和项目架构文档

> 基于当前仓库代码现状整理（前端仓库：`protx-soramv`）。
> 文档目标：帮助研发、测试、产品快速理解系统边界、核心模块、关键链路与后续演进方向。

## 1. 项目定位与范围

AI2OBJ 是一个面向 C 端的多模态 AI 创作平台前端，核心能力覆盖：

- AI 创作：文生图、文生视频、图生图、图生视频、工作流（Workflow）
- 资产管理：工作台文件管理、回收站、存储节点、媒体工具
- 社区生态：内容发布、频道、挑战、互动（点赞/收藏/关注）
- 商业化：充值支付、订单管理、提示词市场
- 扩展业务：OpenRobotX（公司/机器人/资讯）、Resume（在线简历）

## 2. 技术栈与工程基线

### 2.1 前端基础框架

- React 18（`react` / `react-dom`）
- React Router v6（路由分发与鉴权守卫）
- CRA 体系（`react-scripts` 5）
- TypeScript + JavaScript 混合开发（`allowJs: true`）

### 2.2 UI 与样式体系

- Ant Design 5（组件库、主题 token、消息系统）
- styled-components（组件级样式）
- Bootstrap（响应式与部分基础样式）
- Framer Motion（动画交互）

### 2.3 网络与数据

- Axios 统一实例（`src/api/axios.js`）：
  - 动态 baseURL（按域名切换环境）
  - 请求注入 JWT
  - 401/403 统一弹窗与登录跳转
- API 模块化封装（`src/api/*`）

### 2.4 生态能力

- 国际化：`react-intl` + 11 语种字典
- 对象存储：腾讯云 COS SDK（分片上传、断点续传、自动续期）
- 文件加解密：CryptoJS（客户端）

### 2.5 构建与部署

- 包管理：Yarn 1（`packageManager: yarn@1.22.22`）
- 构建：`CI=false react-scripts build`
- 已有部署脚本：Netlify
- 文档中明确兼容 Cloudflare Pages（需固定 Yarn 版本）

## 3. 系统分层架构

当前项目整体呈现典型前端分层：

1) **展示层（Pages + Components）**
- 页面装配与交互逻辑位于 `src/pages`
- 通用组件位于 `src/components`

2) **状态与上下文层（Contexts + Hooks）**
- `LocaleContext`：语言状态与切换
- `FileContext`：工作台文件状态与操作
- 各业务模块内部 hooks 承担局部状态管理

3) **业务服务层（Services）**
- `fileService`：文件列表、重命名、回收逻辑
- `storageService`：存储节点与容量统计
- `cosService`：COS 上传/删除/续期

4) **接口访问层（API）**
- `src/api/axios.js` 提供统一请求能力
- `src/api/*.js|ts` 按业务域拆分接口

5) **工具与模型层（Utils + Models）**
- `utils` 提供格式化、文件、错误处理、加密能力
- `models` 提供 TS 数据模型边界（文件、分页、用户等）

## 4. 核心入口与路由架构

### 4.1 应用入口

- `src/index.js`：挂载 React Root、初始化 `react-modal`
- `src/App.js`：全局容器（主题、国际化、路由、守卫）

### 4.2 全局容器能力（`App.js`）

- `ConfigProvider`：Ant Design 全局主题与组件 token
- `ThemeProvider`：深浅主题状态 + 本地持久化
- `LocaleProvider`：语言上下文 + `IntlProvider`
- `BrowserRouter`：全局路由与页面分发
- `PrivateRoute`：登录鉴权守卫（基于 `localStorage.token`）

### 4.3 路由域划分

- 公共访问：`/`、`/login`、`/signup`、`/openrobotx/*`、部分政策页
- 工作台主域：`/workspace/*`（大部分需登录）
- 社区域：`/community/*`（已接入登录保护）
- 商业化域：`/recharge`、`/orders`、`/billing`
- 特殊域名分流：`seedance2.cn` 对首页与特定路由有直达策略

## 5. 业务模块架构（按领域）

### 5.1 Workspace（核心工作台）

关键入口：
- `src/pages/Workspace/index.js`
- `src/pages/Workspace/Create/index.tsx`

能力拆分：
- Create（创作中心）：文生图、文生视频、图生图、图生视频、工作流
- AllFiles / Trash / Folders：文件资产管理
- StorageNodes：用户存储节点管理
- PromptMarket：提示词市场（工作台内入口）
- Embedding：向量模型与 API Key
- MediaTools：音视频图片压缩工具

特点：
- 工作台采用侧栏聚合 + 子域按路由驱动
- Create 模块通过后端配置控制可用创作类型
- 文件能力与 COS 上传链路耦合紧密

### 5.2 Community（社区）

## 6. API 架构与接口分域

当前 API 按业务拆分如下：

- `auth.js`：登录注册、用户信息、Google 授权
- `payment.js`：充值、订单、支付方式、货币与套餐
- `settings.js`：用户系统设置（读取/更新/重置）
- `community.ts`：帖子、频道、互动、挑战、关系、角色申请、审核
- `openrobotx.js`：公司/机器人/资讯/编年史
- `resume.js`：简历多模块 CRUD
- `embedding.js`：向量生成、API Key 管理
- `modelInteraction.ts`：模型点赞与收藏
- `base.js`：平台通用 + 工作流 + 节点配置 + PromptMarket 等综合接口

说明：
- `base.js` 体量较大，已承担“综合网关”角色，是后续解耦重点。

## 7. 数据流与关键调用链

### 7.1 认证请求链路

`Page` -> `api/auth` -> `api/axios instance` -> Backend API

关键机制：
- 请求前自动注入 JWT
- 响应中遇到 401/403 时统一弹窗并清理本地 token

### 7.2 文件管理链路（Workspace）

`Workspace 页面/Hook` -> `services/fileService` -> `api/axios`

文件上传/删除涉及双链路：
- 元数据：通过后端文件接口管理
- 实体文件：通过 `cosService` 与腾讯云 COS 交互

### 7.3 COS 上传链路

`页面上传动作` -> `cosService.init()` 获取临时凭证 -> 分片/普通上传 -> 进度回调 -> 上传完成后回写业务数据

增强能力：
- 分片上传、暂停恢复
- 上传速度计算
- token 到期自动续期

## 8. 国际化、主题与配置体系

### 8.1 国际化

- 语言包目录：`src/locales/*`
- 支持 11 种语言
- `LocaleContext` 支持：
  - URL 参数识别
  - localStorage 持久化
  - 浏览器/系统语言自动检测

### 8.2 主题

- 默认深色模式（可被用户设置覆盖）
- `App.js` 中集中定义 Ant Design Token
- 支持系统主题联动（auto 模式）

### 8.3 环境变量（当前代码可见）

- `REACT_APP_API_URL`：本地/指定 API 地址
- `REACT_APP_API_BASE_URL`：基础配置接口地址（用于 `api/index.js` 中配置项）

## 9. 目录建议视图（当前实现）

```text

  pages/         # 页面级业务模块（Workspace/Community/OpenRobotX/Resume/...）

```

## 10. 当前现状评估与技术债

### 10.1 现状亮点

- 核心业务域边界总体清晰（Workspace / Community / OpenRobotX / Resume）
- API 已具备按域拆分基础
- 工作台链路对文件与存储管理支持较完整
- 国际化和主题系统成熟，可跨业务复用

### 10.2 已观察到的技术债（客观）

- **JS/TS 混合开发明显**：类型覆盖不均衡，跨模块维护成本高
- **`base.js` 职责偏重**：聚合过多业务接口，不利于协作与演进
- **重复调用逻辑存在**：如语言列表获取在多页面重复实现
- **依赖可能冗余**：安装包中存在疑似未落地依赖（建议定期清理）
- **部分硬编码配置**：例如本地协同地址、少量策略写死于前端

## 11. 架构演进建议（分阶段）

### 短期（1-2 个迭代）

- 将 `base.js` 按工作流、PromptMarket、配置中心继续拆分
- 抽取通用 hooks（语言配置拉取、用户设置拉取、错误处理）
- 建立“接口模型 + UI 模型”转换层，减少页面直接依赖后端字段

### 中期（1-2 个月）

- 统一状态策略（Context + Hooks 规范化，减少 localStorage 直读散落）
- 推进高频模块 TS 化（Auth、Community、Resume 页面层）
- 为关键链路补充自动化测试（认证、支付、上传、发布流程）

### 长期（持续）

- 建立业务域文档与 ADR（架构决策记录）
- 引入性能监控与错误上报闭环
- 逐步形成可配置化创作能力（更多由后端 schema 驱动）

## 12. 结论

项目已经形成可支撑多业务域并行演进的前端架构基础：统一入口、统一鉴权、统一主题与国际化、按域拆分的 API 与工作台主业务闭环都已建立。后续重点应从“功能可用”转向“架构可持续”，优先治理接口层职责聚合、类型一致性与重复逻辑问题，以降低迭代成本并提升稳定性。
